# jev-bitcoin

ビットコインについての自由な質問に、フクロウが答えるページです。質問を打って手を止めると、
それが**用意してある質問のどれかに十分近ければ**、その答えがすぐに返ってきます。
ビットコインを理解する土台になる、お金・金融制度・暗号や分散システムの一般的な質問にも答えます。

https://ocknamo.github.io/sandbox/bitcoin/ （ソースは [`web/`](web)、ビルド結果は
[`../docs/bitcoin/`](../docs/bitcoin)）

> **いまの状態：** 質問 1075 問（20 カテゴリ）のうち 1032 問に回答が入っています。回答は
> 用意した回答案を一次資料と突き合わせて確認したもので、2026-09-26〜27 時点の内容です。
> 18〜20 の棚（お金・貨幣・信用・経済史／銀行・決済・金融制度／インターネット・暗号・分散システム）は
> ビットコインを主語にしない一般論で、物々交換起源説のように「説明のためのモデル」と「歴史的事実」を
> 区別して書いています。日本銀行・金融庁などの一次資料で確かめられた答えには出典を付けています。
> 基礎知識の棚など入門的な質問は、最初に見える答えを専門用語を使わないやさしい説明にし、
> 正確な技術的説明は「もっと詳しく」に置いています。回答に出てくる専門用語（ビザンチン将軍問題、
> P2P、ノード、マイナー、承認など）は「〇〇とは何ですか？」の質問として、それぞれの棚に個別に入っています。
> 回答の書き方は [`internal/faq/data/answers/README.md`](internal/faq/data/answers/README.md)。

## 基本方針：答えはあらかじめ用意したものだけ

[Jev](https://docs.typesafe.ai/introduction) は文章を生成しません。返ってくるのは
`noul` / `choice` / `score` の型付きの値だけです。したがってこのボットは
**「質問 → 用意した質問のどれか」を当てる分類器**で、答えの文章はあらかじめ用意して
リポジトリに置きます。その場で答えを作文することはありません。

ビットコインという題材では、これは制約ではなく利点です。

- **その場で作られた誤答が出ません。** 発行上限や秘密鍵の扱いでモデルが一行でも作文すると、
  それが間違っていたときの被害が大きい。答えはすべて事前に確認でき、プルリクエストで
  レビューできます。
- **答えられないときは、答えられないと言えます。** 外れた質問はログに残るので、
  次に書くべき答えがわかります。
- **答えに出典と「いつ時点の事実か」を付けられます。**

## カテゴリ → 質問の 2 段で分類する

### なぜカテゴリに分けるのか

1. **`choice` の選択肢は 255 個まで。** 質問は 1075 問あります。
2. **`choice` の確率は合計 1。** 似た質問が数百並ぶと票が割れ、正解でもしきい値を越えにくくなります。
3. **`not_for` をカテゴリ単位で書けます。** 「ライトニングの手数料」と「オンチェーンの手数料」の
   区別は、全体の一覧より棚の説明で書くほうが効きます（[`categories.json`](internal/faq/data/categories.json)）。

### single：1 リクエストに畳む

論理的には「カテゴリを選ぶ → その中で質問を選ぶ」の 2 段です。`ROUTER_MODE=single` では**往復は 1 回**で、
1 リクエストの中に

| キー | 型 | 内容 |
| --- | --- | --- |
| `category` | `choice`（20 カテゴリ + `none`） | どの棚の質問か |
| `in_<カテゴリ>` × 20 | `choice`（その棚の質問 + `none`） | 棚の中のどの質問か |
| `kind` | `choice`（質問 / 挨拶 / 投資助言の要求 / ビットコインとその土台以外 / 無意味） | 外れたときの返し方 |
| `level` | `choice`（初心者 / 中級 / 技術者） | 「もっと詳しく」を最初から開くか |
| `multi` | `noul` | 一度に複数の質問をしているか |

を全部入れます。質問は並列に評価されるので、棚が 20 あっても待ち時間はほとんど増えません。
ただし **Jev は入力トークンで課金**するので、棚はすべての入力に毎回付いて回ります。
1 リクエストはおよそ 110 KB で、CI の実測は **1 問あたり 47,000 トークン**（137 問で 6,438,171）。
コンテキストの上限（64k トークン）には収まっていますが、1 問増えるごとにおよそ 45 トークン増えます。
この実測は 17 棚・840 問のときのもので、18〜20 の棚を足したいまは 1 リクエストがおよそ 135 KB
（比例で見積もって 58k トークン前後）になり、single のまま足せる余地はほとんど残っていません。
**既定は下の two_stage** で、single は比較用に残しています。

スコアは Go 側で合成します（[`internal/router`](internal/router/router.go)）。

```
score(q) = P(category = c) × P(q | c)
```

**カテゴリの 1 位だけを信じません。** 「ライトニングの手数料って誰が決めるの」は
`lightning 0.50 / transactions 0.45` のように割れます。1 位に絞ると、正解が
`transactions` 側にあったときに取り逃します。全部の棚を確率つきで読めば、
跨った質問はどちらからも届きます（テストの `TestReadsEveryShelf`）。

各棚の `choice` には必ず `none` を入れ、**棚の中で `none` に負けた質問は、棚の確率が
いくら高くても答えにしません**。関係のない入力がその棚で一番ましな質問に流れ込むのを防ぐためです。

### two_stage（既定）：2 往復に分けて、要る棚だけ聞く

two_stage では、1 回目でカテゴリ・`kind`・`level`・`multi` だけを聞き、
2 回目で **P(c) が `min(Floor, Match − Margin)`（既定 0.15）以上の棚だけ**を聞きます。合成式も判定も同じです。

**これで判定は single と変わりません。** 質問の点は P(c) × P(q|c) なので、聞かなかった棚の質問は
どれも 0.15 未満です。`Floor` 未満なので答えにも「もしかして」にもならず、`Match − Margin` 未満なので
2 位として 0.40 以上の 1 位を止めることもありません。失われるのは画面に出ない 0.15 未満の候補
（外れたときのログの「近かった質問」）だけです。乱数で作った 3000 通りのモデルの答えで、
single と同じ結論になることをテストしています（`TestTwoStageConcludesAsSingle`）。
前提は、モデルがカテゴリや棚の問いに、同じリクエストに何が並んでいるかと関係なく答えることです
（問いは並列に評価されます）。下の実測はこれと矛盾しません。

同じコミットで両方を流した CI の Live（137 問）の結果です。

| | single | two_stage |
| --- | --- | --- |
| 1 問のリクエスト | 1 | 1.97（`none` に振られた入力は 1） |
| 1 問の入力トークン | 46,993 | **13,478**（約 71% 減） |
| 最悪の入力トークン（計算） | 約 47k | 約 31k（0.15 以上の棚は最大 6 つ） |
| 1 問の待ち時間 | 0.33 秒 | 0.33 秒（2 往復だが、それぞれが小さい） |
| 質問を足したとき | 1 問ごとに全リクエストが約 45 トークン増える | 増えるのはその棚が選ばれたときだけ |

1 回目の約 12k のうち 9 割はカテゴリの説明（`categories.json` の `what` / `not_for` / `examples`）で、
質問の数では増えません。棚の大きさは最大の `security`・`history` でも 8 KB ほどです。

18〜20 の棚を足したあとの two_stage の Live（154 問）では、1 問の入力トークンは **16,301**（約 21% 増）、
正答は 141 問（92%）でした。増えた分は主に、1 回目のリクエストに毎回付く 3 棚ぶんのカテゴリの説明です。

正答は同じ実行で single 114 問、two_stage 117 問でした。結論が食い違った問は 5 つ（状態が違ったのは 3 つ）です。
一方、同じコーパスで single を 2 回流しても、結論は 8 問、状態は 4 問で食い違いました。最上位の点の揺れも、
single 同士と single 対 two_stage で同じ（平均 0.017）です。モデルの答えは実行ごとに揺れますが、
two_stage にしたことによる劣化はその揺れの中に見えません。

## 判定（Go 側の `Policy`）

Jev には「その入力は何か」だけを聞き、採用するかは Go で決めます。

| 結果 | 条件 | 画面 |
| --- | --- | --- |
| `answer` | 1 位が `Match`（0.40）以上、`none` に勝っている、2 位との差が `Margin`（0.15）以上 | 答え |
| `suggest` | 1 位が `Floor`（0.15）以上だが、上の条件を満たさない | 「もしかして」で候補を最大 3 つ |
| `miss` | それ以外 | `kind` ごとの決まった文面 |
| `multiple` | `multi` が `Multi`（0.60）以上。上のどれよりも優先 | 「ひとつずつ質問してください」＋近い質問を最大 3 つ |

### 一度に複数の質問をされたら

答えは質問ひとつにつきひとつです。「ライトニングって何？あと誰が作ったの？」に、たまたま
点の高かった一方だけ答えると、もう一方を黙って落とすことになります。そこで `multi`（`noul`）で
「別々の答えが要る質問が 2 つ以上あるか」を聞き、そうなら答えずに**ひとつずつ聞いてもらいます**。
分類はそのまま行っているので、近い質問は候補として出します（読み手はそこから始められます）。

`kind` の選択肢にしなかったのは、複数の質問も「質問」だからです。選択肢にすると `question` と
票を取り合い、どちらかが負けます。「UTXO って何？初心者向けに」のように**同じ点への補足**は
1 問として扱うよう、質問文で明示しています。

`Margin` があるのは、似た質問が並んでいるからです（4-8「同じアドレスを何度も使っても
問題ありませんか？」と 4-9「アドレスを再利用するとどんな問題がありますか？」）。
僅差なら当てずっぽうに片方を選ばず、両方を出します。

`kind` は外れたときの文面を選ぶだけで、答えを止めません。「ただの投資商品ではないの？」は
投資の話にも見えますが、用意した質問に当たるなら答えます。

「もしかして」の候補や関連する質問を押しても Jev は呼びません。番号で
`GET /api/faq/{id}` を引くだけです。

## ページ（kanabun）

大きなフクロウと、その下に入力欄が一つだけあります。**送信ボタンはありません。**

- **5 文字以上**入っていて、**入力が 0.5 秒止まったら**、その文を質問として送ります
- **IME で変換中は送りません。** 変換前のかなは、まだ質問ではありません
- **同じ文は続けて送りません**（空白の違いは同じ文とみなします）
- **最新の質問への返事だけを表示します。** 遅れて届いた古い返事は捨てます
- Enter でもすぐに送れます（5 文字以上のとき）

フクロウの様子で状態がわかります。読んでいる間は首をかしげて上を見、答えがあれば跳ね、
わからなければ首を傾け、いっぺんに聞かれると目を回します。吹き出しの台詞も変わります。

**声でも質問できます。** 入力欄の右端のマイクを押して話すと、聞き取った言葉がそのまま欄に
出て、話し終えたところで質問します（入力の止まりを待たずに、すぐ送ります）。ブラウザの
Web Speech API（`SpeechRecognition`、Chrome などでは `webkitSpeechRecognition`）を `ja-JP` で
使っていて、ライブラリもこちらのサーバも使いません（[`web/src/voice.ts`](web/src/voice.ts)）。

- 対応していないブラウザ（Firefox など）ではマイクのボタン自体を出しません
- 聞いている間はボタンが塗られて脈打ち、フクロウは身を乗り出して「どうぞ、お話しください。」と言います
- もう一度押すと止まり、そこまでに聞き取った言葉で質問します。途中でキーボードを打つと音声入力は止まります
- 5 文字に満たない聞き取りは送らず、欄に残して手で続きを書けるようにします
- マイクの拒否・マイクなし・無音・接続失敗は、それぞれ何をすればいいかを日本語で出します
- **音声がどこで処理されるかはブラウザ次第です。** Chrome などでは音声がブラウザ提供元のサーバで
  認識されるため、聞いている間はそのことを入力欄の下に書いています
- マイクは HTTPS のページでしか使えません（GitHub Pages は HTTPS なので問題ありません）

**自分の質問の履歴を見られます。** 答えの下の「これまでの質問」に、新しい順に最大 50 件並びます。
答えが見つかった質問を押すとその答えを開き（無料、モデルを呼ばない）、見つからなかった質問を
押すともう一度聞きます。

- 履歴は**そのブラウザの localStorage にだけ**保存します。サーバには送らず、画面にもそう書いてあります
- 自動送信なので、打ちかけの文（「ビットコインって」→「ビットコインって何？」）が 1 分以内に
  続いたら、別の行にせず最後の 1 件にまとめます
- 「もしかして」から候補を選んだら、その質問の行に選んだ答えを結び付けます。複数質問から
  選んだ場合は結び付けません（その 1 問が質問全体の答えではないため）
- 「履歴を消す」で消せます。ストレージが使えない環境（プライベートウィンドウなど）では、
  履歴が残らないだけで他は同じように動きます

**自分の質問と答えを SNS に共有できます。** 答えの下の「この質問と答えを共有する」を開くと、
投稿される文面をそのまま見せたうえで、「共有する」（Web Share API、対応端末のみ）と「コピー」を出します
（[`web/src/share.tsx`](web/src/share.tsx)）。

- 文面は「Q. 自分が打った質問」「A. 答えの冒頭（最初の一文、長ければ 60 文字で切る）」「#jevbitcoin」とリンクです。
  質問は 50 文字で切ります。日本語で X の 1 ポスト（280、全角は 2 と数える）に収まる長さです
- 「もしかして」や履歴から開いた答えでも、Q は自分が打った質問です。`#1-7` や関連する質問から開いた答えは、
  用意した質問の文面を Q にします
- リンクは答えの番号（`#1-7`）なので、リンクを開いた人は Jev を呼ばずに答えを読めます。`?api=` は外します
- 回答が準備中の質問には出しません

**質問の一覧は表示しません。** API にも一覧を返すエンドポイントはありません。

`#1-7` のようなハッシュを付けると、その質問の答えを開きます（答えの右上の番号がそのリンクです）。

```sh
cd web
bun install
bun run dev      # 開発サーバ。?api=http://localhost:8080 でローカルのサーバに向ける
bun run build    # ../../docs/bitcoin/ を作り直す
```

jev-mystery と同じく、**ビルド結果をコミット**し、CI で再ビルドして差分が出ないことを確かめます。
Bun の版は `.bun-version`（1.4.2）で固定しています。

### kanabun で踏んだこと

**SVG は JSX で書けません。** kanabun は全要素を `document.createElement` で作るので、
`<svg>` も HTML 名前空間の未知の要素になり、何も描かれません。フクロウは固定の文字列として
`ref` で `innerHTML` に入れています（利用者の入力は混ざらない自前の定数なので安全です）。
中の `bird` / `pupils` / `lid` クラスをページの CSS で動かしています。

**`css` の中の `@keyframes` はグローバルです。** 名前は `owl-` で始めています。

## API

| エンドポイント | 役割 |
| --- | --- |
| `POST /api/ask` | `{"question": "…"}` を分類して結果を返す。Jev を 2 回（`none` に振られた入力は 1 回、single なら 1 回）呼ぶ |
| `GET /api/faq/{id}` | 番号で答えを返す。Jev を呼ばない |
| `GET /health` | デプロイパイプラインが叩く |

```json
{
  "status": "answer",
  "kind": "question",
  "answer": {
    "id": "1-7", "title": "1 BTCは何satoshiですか？",
    "category": {"id": "basics", "name": "基礎知識"},
    "answered": true, "answer": ["…"], "more": ["…"],
    "related": [{"id": "1-12", "title": "…", "category": {…}, "answered": true}],
    "sources": ["…"], "updated": "2026-09-26"
  },
  "expand": false,
  "categories": [{"id": "basics", "name": "基礎知識", "p": 0.9}]
}
```

**状態はサーバに持ちません。** 1 問 1 答で完結します。

**レート制限とキャッシュ。** 1 質問 = 有料 API 2 リクエスト（入力トークンでおよそ 13k）で、ページは入力が止まるたびに
送るので、1 人が 1 問書くあいだに数回飛ぶことがあります。IP ごとに**直近 30 分で 30 回まで**の制限と、
入力 → 結果の LRU キャッシュ（1024 件）を入れています。31 回目はその時点から 30 分間、その IP からの
質問をすべて断り（キャッシュに当たるものも含む）、429 と「あと何分」のメッセージを返します。
キャッシュに当たった質問は回数に数えません。

キャッシュは、全角と半角、大文字と小文字、空白と句読点（文中も含む）の違いを無視して同じ質問とみなします
（「ビットコイン、とは何ですか？」と「ビットコイン とは何ですか」は同じ）。よく打たれる用語は、
書き方が違っても同じ単語として扱います（「ビットコイン」「Bitcoin」「BTC」、「ライトニング」と「Lightning」、
「ネットワーク」と「Network」、「サトシ・ナカモト」と「Satoshi Nakamoto」、「サーバ」と「サーバー」、
「コンピュータ」と「コンピューター」、「ユーザ」と「ユーザー」）。ただし、数字に挟まれた句読点と `%` は残します
（「1.5BTC」と「15BTC」は別）。違う質問を同じとみなすと別の答えを返してしまいますが、同じ質問を別とみなしても
API を 1 回余分に呼ぶだけなので、迷うものは別の質問として扱います。キャッシュはインスタンスのメモリにあるので、
インスタンスが止まったりデプロイし直したりすると空になります。

**外れた質問はログに残します**（`"msg": "unanswered"`、入力と近かった質問の番号）。
自動送信なので、打ちかけの文も残ります。

## 構成

```
cmd/server/            Cloud Run のエントリポイント
cmd/cli/               正答率を測るベンチ
internal/jev/          System One API のクライアント（jev-mystery からのコピー）
internal/faq/          コーパスの型・読み込み・検証
internal/faq/data/     categories.json / questions.tsv / answers/*.md（バイナリに埋め込み）
internal/router/       質問の組み立て、P(c)×P(q|c) の合成、Policy
internal/server/       HTTP、レート制限、キャッシュ、外れたときの文面
web/                   フロントエンド（kanabun）
testdata/queries.tsv   CLI が流す質問と、当たるべき番号
```

コーパスは起動時に全部読み込んで検証します。番号の重複、カテゴリの取り違え
（`2-1` が基礎知識に入っている等）、存在しない番号への回答や `関連:` があると、
**サービスが起動しません**。

## 動かす

```sh
export TYPESAFE_API_KEY=...
go run ./cmd/server           # http://localhost:8080
```

| 環境変数 | 既定値 | 内容 |
| --- | --- | --- |
| `TYPESAFE_API_KEY` | （必須） | 無いと起動しない |
| `JEV_MODEL` | `jev-latest` | モデル識別子 |
| `ROUTER_MODE` | `two_stage` | `single` で 1 往復にまとめる（入力トークンは 3 倍以上） |
| `MATCH_THRESHOLD` / `MARGIN_THRESHOLD` / `FLOOR_THRESHOLD` | 0.40 / 0.15 / 0.15 | しきい値 |
| `MULTI_THRESHOLD` | 0.60 | 一度に複数の質問をしているとみなす `noul` |
| `QA_DEBUG` | | `1` でモデルの生の数字をレスポンスに含める（調整用） |
| `TYPESAFE_ENDPOINT` | | 接続先の差し替え（スタブ用） |

## 測る

このボットの成否は、**実際に打たれる日本語が、狙った質問に当たるか**の一点です。

```sh
go run ./cmd/cli -queries testdata/queries.tsv       # -v で候補ごとの数字、-mode single で比較
```

`queries.tsv` は `入力<TAB>期待`。期待は質問番号、`none`（何にも当たらないのが正解）、
`multi`（複数の質問として返すのが正解）、`kind:advice` などです。最後に正答数と、**取り違えたカテゴリの組**（どの棚の `not_for` を
直すべきか）、1 問あたりの入力トークン数とリクエスト数が出ます。

**入力は `questions.tsv` の文面から取らないでください。** モデルに見せている文をそのまま
打ち込むテストは、何も測っていません。

実際の API で流すのはトークンを食うので、通常の CI では流しません。測りたいコミットを
専用ブランチ `jev-bitcoin-live` にプッシュすると、[`jev-bitcoin-live.yml`](../.github/workflows/jev-bitcoin-live.yml)
が既定の two_stage で流し、結果をジョブのサマリーに出します（`TYPESAFE_API_KEY` が無ければスキップ）。

```sh
git push -f origin HEAD:jev-bitcoin-live
```

## 次にやること

1. 回答を書く（`internal/faq/data/answers/`）。書いたら事実関係を検証する
2. CLI の結果を見て、カテゴリの `not_for` としきい値を調整する
3. 外れた質問のログから、足りない質問を足す
