# jev-bitcoin（設計）

ビットコインについての自由な質問に答えるボットです。ユーザーは文章で質問を書き、
それが**用意してある質問のどれかに十分近ければ**、その答えを返します。

> この文書は実装前の設計です。まだコードはありません。

## 基本方針：答えは人が書く

[Jev](https://docs.typesafe.ai/introduction) は文章を生成しません。返ってくるのは
`noul` / `choice` / `score` の型付きの値だけです。したがってこのボットは
**「質問 → 用意した Q&A のどれか」を当てる分類器**で、答えの文章はすべて人間が書いて
コーパス（JSON）に入れておきます。jev-mystery の「プレイヤーが読む文章はすべて人間が
書いたもの」と同じ構造です。

これは制約ではなく、ビットコインという題材ではむしろ利点です。

- **もっともらしい誤答が出ません。** 発行上限、半減期、秘密鍵の扱いのような話で
  モデルが一行でも作文すると、それが間違っていたときの被害が大きい。答えは全部
  レビューできる場所（リポジトリ）にあります。
- **答えられないときは、答えられないと言えます。** 分類が `none` に倒れたら
  「まだ答えを用意していません」と返し、その質問をログに残してコーパスを育てます。
- **答えに出典と更新日を付けられます。** ブロック報酬のように時期で変わる事実は
  エントリごとに `updated` を持たせます。

「なんでも答える」は、**なんでも受け付けて、当たるものがあれば必ず人の書いた答えを返し、
無ければ正直に外す**、という意味で実現します。

## 2 段階の分類：カテゴリ → 質問

### なぜカテゴリに分けるのか

1. **`choice` の選択肢は 255 個まで。** Q&A はすぐにそれを超えます。
2. **`choice` の確率は合計 1。** 似た質問が 200 個並ぶと票が割れて、正解でも
   しきい値を越えにくくなります（jev-mystery で「行動が増えると共倒れする」と書いた現象）。
3. **`not_for` をカテゴリ内で局所的に書けます。** 「ライトニングの手数料」と
   「オンチェーンの手数料」の区別は、全体の一覧より同じ棚の中で書くほうが効きます。

### 1 リクエストに畳む

論理的には「カテゴリを選ぶ → そのカテゴリの中で質問を選ぶ」の 2 段ですが、
**往復は 1 回にします**。1 リクエストの中に

- `category`: カテゴリ全体の `choice`（+ `none`）
- `q_<カテゴリID>`: カテゴリごとの質問の `choice`（+ `none`）× カテゴリ数

を全部入れます。質問は並列に評価されるので、カテゴリが 10 個あっても待ち時間は
ほとんど増えません。**高いのは質問の数ではなくリクエストの数**です（jev-nostr / jev-mystery
で確かめた前提）。

最終的なスコアは Go 側で合成します。

```
score(q) = P(category = c) × P(q | c)      （q はカテゴリ c の質問）
```

- 「カテゴリの中で一致率が高い質問を選ぶ」をそのまま確率で書いたものです。
- **カテゴリの argmax だけを信じません。** 「ライトニングで送るときの手数料は？」は
  `lightning 0.55 / fees 0.40` のように割れます。argmax で `lightning` に絞ると、
  正解が `fees` 側にあったときに取り逃します。全カテゴリの `P(c) × P(q|c)` を並べれば、
  跨った質問も自然に拾えます（jev-nostr のトピックを「足し算で読む」のと同じ考え方）。
- カテゴリ内の `choice` には必ず `none` を混ぜます。関係ないカテゴリでは `none` が勝ち、
  そのカテゴリの質問のスコアは小さくなります。

### コーパスが大きくなったら 2 往復に切り替える

1 リクエストのコンテキストは 64k トークンです。質問 1 件の説明（`what` / `not_for` /
`examples`）をおよそ 100〜150 トークンとすると、**全カテゴリを 1 リクエストに入れられるのは
300 件前後まで**です。それを超えたら、

1. 1 回目：`category` だけを聞く
2. 2 回目：`P(c)` の上位から累積 0.8 に達するまで（最大 3 カテゴリ）の `q_<c>` だけを聞く

に切り替えます。合成式は同じです。切り替えは設定値（`MODE=single|two_stage`）にして、
CLI で両方の正答率を比べられるようにします。

## 同じリクエストで一緒に聞くこと

| キー | 型 | 使い道 |
| --- | --- | --- |
| `category` | `choice`（カテゴリ + `none`） | 上の合成式の `P(c)` |
| `q_<カテゴリ>` | `choice`（そのカテゴリの質問 + `none`） | 上の合成式の `P(q\|c)` |
| `kind` | `choice`（質問 / 挨拶 / 投資助言の要求 / ビットコイン以外 / 無意味） | 外れたときの返し方を選ぶ |
| `level` | `choice`（初心者 / 中級 / 技術者） | 答えの「詳しく」を最初から開くか |

- `kind` が「投資助言の要求」（「今買うべき？」「来年いくらになる？」）なら、
  コーパスの当たり外れに関係なく**決まった文面**で断ります。価格予想の Q&A を作るより、
  型で先に弾くほうが確実です。
- `kind` は分類の受け皿でもあります。「こんにちは」が `basics` の何かに吸い込まれるのを防ぎます。
- `level` は答えの中身を変えません（答えは人が書いたもの 1 つ）。`answer` と `more` のうち
  どこまで最初から見せるかだけを変えます。

## 判定（Go 側の `Policy`）

Jev には「その質問は何か」だけを聞き、「それを採用するか」は Go で決めます。
jev-mystery の `game.Policy` と同じ流れです。

| 結果 | 条件 | 画面 |
| --- | --- | --- |
| `answer` | 最上位の `score(q)` が `Match`（既定 0.40）以上、`none` に勝っている、2 位との差が `Margin`（既定 0.15）以上 | 答えを出す |
| `suggest` | 上位はしきい値付近だが、2 位・3 位と差がない | 「もしかして」で候補の質問文を 2〜3 個出す |
| `miss` | 最上位が `Floor`（既定 0.20）未満、または `none` が勝つ | 「まだ答えを用意していません」＋入力をログに残す |
| `refuse` | `kind` が投資助言の要求 | 決まった文面で断る |
| `offtopic` | `kind` がビットコイン以外 / 無意味 / 挨拶 | `kind` ごとの文面 |

**「もしかして」の候補をクリックしても Jev は呼びません。** 候補は ID で返っているので、
`GET /api/faq/{id}` で答えを取るだけです（無料・即時）。関連する質問のリンクも同じです。

既定値は測定値ではなく出発点です。環境変数と CLI のフラグで動かせるようにします。

## コーパスの形

`internal/faq/data/<カテゴリID>.json` に 1 カテゴリ 1 ファイル。バイナリに `go:embed` で
埋め込み、起動時に全部読み込んで検証します（ID の重複、`none` の予約、1 カテゴリ 254 件以内、
`related` の参照先が存在すること）。壊れたコーパスではサービスが起動しません。

```json
{
  "id": "wallet",
  "name": "ウォレットと鍵",
  "match": {
    "what": "ウォレット、秘密鍵、シードフレーズ、バックアップ、ハードウェアウォレット",
    "not_for": "送金の手順や手数料（transactions）、詐欺の手口（security）",
    "examples": ["シードフレーズをなくしたらどうなる？"]
  },
  "questions": [{
    "id": "lost_seed",
    "title": "シードフレーズをなくしたらどうなりますか？",
    "match": {
      "what": "シードフレーズ（リカバリーフレーズ、12/24 単語）を紛失した場合の影響と対処",
      "not_for": "シードフレーズの保管方法そのもの（seed_storage）",
      "examples": ["復元ワードを失くした", "24単語のメモを捨ててしまった"]
    },
    "answer": ["短い答え。2〜4 文。"],
    "more": ["詳しい説明。技術者向けの補足。"],
    "related": ["seed_storage", "hardware_wallet"],
    "sources": ["https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki"],
    "updated": "2026-09-26"
  }]
}
```

`title` は画面に出す**代表的な質問文**で、「もしかして」やカテゴリ一覧に使います。
`match` はモデルにだけ渡します（隠す必要はありませんが、レスポンスに載せる理由もありません）。

### カテゴリ案（最初の 10 個）

| ID | 名前 | 例 |
| --- | --- | --- |
| `basics` | ビットコインとは | 誰が管理している？ブロックチェーンとは？ |
| `wallet` | ウォレットと鍵 | シードフレーズ、ハードウェアウォレット、カストディ |
| `transactions` | 送金と手数料 | 手数料の決まり方、承認時間、UTXO、RBF |
| `mining` | マイニングと合意 | PoW、難易度調整、半減期、電力 |
| `economics` | 発行と価値 | 2100 万枚、インフレ、なぜ価値がある？ |
| `lightning` | ライトニング | チャネル、インボイス、ライトニングの手数料 |
| `security` | セキュリティと詐欺 | よくある詐欺、量子計算機、51% 攻撃 |
| `privacy` | プライバシー | 匿名性、アドレスの再利用、CoinJoin |
| `history` | 歴史と文化 | サトシ・ナカモト、ピザの日、フォーク |
| `protocol` | プロトコルとノード | フルノード、Taproot、BIP、Script |

「税金」「どこで買えるか」は国と時期で答えが変わるので、最初は `kind` と同じ扱いで
**決まった文面（専門家・公的情報への誘導）**にとどめます。

**`not_for` を必ず書きます。** jev-nostr で `tech` / `bitcoin` / `nostr` は `not_for` が
無いと `tech` が他を飲み込みました。ここでは `basics` が一番の吸い込み口になるはずです。

## 構成

```
ブラウザ ──POST /api/ask──> Cloud Run ──> api.typesafe.ai
 （kanabun、                 （コーパスと       （カテゴリと質問を分類）
   docs/bitcoin/）             API キーを持つ）
```

| エンドポイント | 役割 |
| --- | --- |
| `POST /api/ask` | `{"question": "…"}` を分類して結果を返す。Jev を 1 回（two_stage なら 2 回）呼ぶ |
| `GET /api/faq/{id}` | ID で答えを返す。Jev を呼ばない |
| `GET /api/catalog` | カテゴリと各質問の `title` の一覧（ブラウズ用） |
| `GET /health` | デプロイパイプラインが叩く |

`/api/ask` のレスポンス:

```json
{
  "status": "answer",
  "answer": {
    "id": "lost_seed", "category": "wallet", "title": "…",
    "answer": ["…"], "more": ["…"], "expand": false,
    "related": [{"id": "seed_storage", "title": "…"}],
    "sources": ["…"], "updated": "2026-09-26"
  },
  "candidates": [
    {"id": "lost_seed", "title": "…", "score": 0.71},
    {"id": "seed_storage", "title": "…", "score": 0.12}
  ],
  "categories": {"wallet": 0.82, "security": 0.10}
}
```

`candidates` と `categories` は常に返します。ページが「なぜこの答えなのか」を小さく
見せるのに使います（jev-nostr の「根拠を表示する」と同じ方針）。

**状態はサーバに持ちません。** 1 問 1 答で完結するので、jev-mystery のような署名付き
トークンも要りません。追質問（「それってどういう意味？」）への対応は後回しにして、
やるときは直前の Q&A の ID をリクエストに載せ、その答えを `state` に入れて分類させます。

### パッケージ

| パッケージ | 役割 |
| --- | --- |
| `cmd/server` | Cloud Run のエントリポイント |
| `cmd/cli` | 正答率を測るベンチ（下記） |
| `internal/jev` | System One API のクライアント（jev-mystery からのコピー） |
| `internal/faq` | コーパスの型・読み込み・検証 |
| `internal/router` | 質問の組み立て、合成スコア、`Policy` |
| `internal/server` | HTTP、入力の上限、レート制限 |
| `web` | フロントエンド（kanabun）。ビルド結果は `../docs/bitcoin/` |

### 費用とレート制限

1 質問 = 有料 API 1 リクエスト。入力トークン課金（10 億トークンあたり $42）なので、
コーパス全体を毎回送っても 1 問あたり 1 セント未満です。問題は金額より**連打**なので、

- IP ごとのトークンバケット（インスタンス内のメモリで十分）
- 正規化した入力 → 結果の LRU キャッシュ（「ビットコインとは」は何度も来る）
- Cloud Run の最大インスタンス数

を最初から入れます（jev-mystery の「まだ無いもの」に挙がっていた穴を最初に塞ぐ）。

## フロントエンド（kanabun）

`@kanabun/core` + `@kanabun/router`。jev-mystery の `web/` と同じ構成・同じ規約です。

| 画面 | ハッシュ | 中身 |
| --- | --- | --- |
| 質問 | `#` | 入力欄、これまでの Q&A のログ、カテゴリ一覧 |
| 答えの固定リンク | `#<質問ID>` | その答えだけ（`/api/faq/{id}`、Jev を呼ばない） |

コンポーネント:

- `AskBox` — 入力欄。送信中は無効化、スマホでは送信後にフォーカスを外す（jev-mystery と同じ）
- `AnswerCard` — `answer`、「もっと詳しく」で `more`、関連質問、出典、更新日。
  `level` が技術者寄りなら最初から開く
- `Suggestions` — 「もしかして」のチップ。押すと `#<質問ID>` へ
- `Miss` — 外れたときの文面と、近かったカテゴリへのリンク
- `CategoryBrowser` — カテゴリごとの `title` 一覧（`/api/catalog`）
- `WhyBar` — `categories` の上位を細い帯で見せる（任意）

jev-mystery で踏んだ罠をそのまま守ります。

- **コンポーネントのルートは要素ひとつ。** フラグメントを返すと `resource` の fetch が無限ループする
- `<Router>` の children は関数
- 固定リンクは `<Link>` ではなく素の `<a href="#id">`（`navigate` は `#/id` にしてしまう）
- `?api=http://localhost:8080` でローカルのサーバに向けられる
- ビルド結果（`docs/bitcoin/`）をコミットし、CI で再ビルドの差分が出ないことを確かめる。
  Bun の版は `.bun-version` で固定

## 測る

このボットの成否は、**実際に打たれる日本語の質問が、狙った Q&A に当たるか**の一点です。

```sh
go run ./cmd/cli -queries testdata/queries.tsv
```

`queries.tsv` は `入力<TAB>期待する質問ID`（`none` は「当たらないのが正解」、
`refuse` / `offtopic` は `kind` の判定）。出力は

- 全体の正答率と、`answer` / `suggest` / `miss` の内訳
- **カテゴリの混同行列**（どのカテゴリがどこに吸われているか。`not_for` を直す場所がわかる）
- `single` と `two_stage` の比較（`-mode`）

**入力は `match.examples` から取らないでください。** モデルに見せている文を打ち込むテストは
何も測っていません（jev-mystery と同じ注意）。

実際の API 呼び出しは CI の Live ジョブで行い、結果をジョブのサマリーに出します
（`TYPESAFE_API_KEY` が無ければスキップ）。

## 進め方

1. コーパスの骨格：10 カテゴリ × 各 5 問、`queries.tsv` を 100 行
2. `internal/faq` と `internal/router`、CLI で正答率を出す（ここで single / two_stage を決める）
3. `cmd/server` と Cloud Run へのデプロイ（`deploy-jev-bitcoin.yml`、CI のマトリクス追加）
4. kanabun のページ（`docs/bitcoin/`）
5. `miss` ログからコーパスを育てる
6. 追質問、英語対応

## 未決定のこと

- **コーパスを誰がどう書くか。** 初版をこちらで下書きし、事実関係をレビューしてもらう想定です。
- **カテゴリの内側の `none` が本当に効くか。** 合成式は「関係ないカテゴリでは `none` が勝つ」
  ことを前提にしています。効かなければ two_stage に倒します。CLI で最初に確かめる点です。
- **英語の質問を受けるか。** 受けるなら `language` を `choice` で聞き、答えを 2 言語持つか、
  日本語の答えを返すかを決める必要があります。
