# jev-mystery

自由入力の推理ゲームです。プレイヤーは選択肢を見ません。何をしたいかを文章で書き、
それが**その場でできることのどれかに十分近ければ**、その行動が起こります。近いものが
なければ、何も起こりません。

最後に全員を集め、誰がどうやってなぜやったのかを**文章で**書きます。その文章が採点され、
エンディングが決まります。

## なぜ Jev なのか

[Jev](https://docs.typesafe.ai/introduction) は文章を生成しません。返ってくるのは
**コードが直接分岐できる型付きの値**だけです。このゲームで Jev がやるのは二つだけで、
どちらも「読んで分類する」仕事です。

| 場面 | 聞き方 | 使い道 |
| --- | --- | --- |
| 入力 → 行動 | `choice`（その場で可能な行動 + `none`） | どの行動を求めているか |
| 入力の種類 | `choice`（移動 / 調査 / 尋問 / 会話 / メタ / 無意味） | 空振りの文面を選び分ける |
| 締めようとしているか | `noul` | 早すぎる名指しに「まだ早い」と返す |
| **はいかいいえで答えられる質問か** | `noul` | クローズ質問かどうかの判定そのもの |
| 誰に向けた質問か | `choice`（その場の人物 + `none`） | どの口が答えるか |
| その人物なら何と答えるか | `choice`（はい / いいえ / わかりません / 質問ではない） | クローズ質問の返事 |
| **フレーバー** | `choice`（その場のフレーバー + `none`） | 行動に当たらなかった入力の受け皿 |
| 最終回答の犯人 | `choice`（容疑者 + `none`） | 名指しが当たっているか |
| 真相の要素ごと | `noul` × 要素数 | どこまで辿り着いたか |
| 論の筋 | `score`（5段階） | 説明として成立しているか |

1 ターンで聞くのはこれらのうち上半分で、**全部まとめて 1 リクエスト**です。質問は並列に
評価されるので、増えても往復は増えません。

プレイヤーが読む文章は**すべて人間が書いたもの**で、シナリオの JSON に入っています。
モデルは一行も書きません。

**真相をモデルに渡しても漏れません。** 採点のとき、`state` にはその事件の真相がそのまま
入ります。Jev はテキストを返さないので、真相が player に戻る経路が構造的に存在しません。
チャット型の LLM で同じことをすると、真相をプロンプトに入れた時点で漏洩を抱えます。

## クローズ質問

その場にいる人物に、**はい・いいえで答えられる質問**を文章で投げられます。

```
> 望月さん、この館で犬を飼っていましたか
  望月 節子に、はいかいいえで訊いた。
  「いいえ」
```

行動として書かれた質問（`ask_mochizuki` など）は、作者が用意した答えを返します。
クローズ質問はその逆で、**作者が答えを用意していない問いに答えます**。答えるのは人物です。

### ルーティングと同じ土俵に乗せない

以前は「望月に、はいかいいえで訊く」を行動と**同じ `choice` の中**に混ぜていました。これは
動きません。`choice` の確率は合計 1 なので、その場に行動が八つあれば、質問はその八つ全部に
勝たなければ届かない。プレイヤーから見ると「どう書けばクローズ質問になるのか分からない」に
なります（実際そうなりました）。

いまは三つの判定に分けて、**どれも行動と競合しません**。

| 判定 | 型 | しきい値 |
| --- | --- | --- |
| はいかいいえで答えられる質問か | `noul` | `Closed`（既定 0.50） |
| その場の誰に向けたものか | `choice`（人物 + `none`） | `Match` / `Confidence` |
| その人物ならどう答えるか | `choice`（はい / いいえ / わかりません / 質問ではない） | `Answer`（既定 0.50） |

一つめが、レビューで言われた「はいかいいえで答えられる質問かそれ以外かを Jev に判定させる」
そのものです。行動のルーティングとは別の質問なので、**その場に行動がいくつあっても難しく
なりません**。

順番も決めてあります。**作者の書いた行動 → クローズ質問 → フレーバー**。行動が勝つのは、
その問いに対する答えが人の手で書かれているからで、クローズ質問はそれが無いところを埋めます。
そのぶん、行動として書かれた質問の `match.not_for` には「はい・いいえで答える質問ではない」
と書いておく必要があります（書かないと、同じ話題のクローズ質問を行動が飲み込みます）。

| どこに置くか | 何を置くか | なぜ |
| --- | --- | --- |
| `instructions` | その人物が**知っていること**と、**言わないこと** | 人物に属する。同じ出来事を見ていても、誰に訊くかで答えが変わる |
| `state` | 事件の筋書き（`finale.truth`） | 事件に属する。その場の全員で共有される |

質問文は「**その人物なら何と*言う*か**」を聞きます。真実が何かではありません。だから犯人は、
state に入った筋書きを真正面から見ながら「いいえ」と答えます。**嘘が、プロンプトの小細工では
なく型の上で成立します。**

真相を state に入れても漏れません。Jev はテキストを返さず、返るのは 4 択の 1 つだけです。
この機能はチャット型の LLM では原理的に危うく、Jev では原理的に安全です。

### 4 択のうち 1 つはプレイヤーに見せません

`はい` / `いいえ` / `わかりません` に加えて、**「そもそも、はい・いいえで答えられる質問ではない」**
という選択肢があります。これが無いと、質問でない入力にも三択のどれかが返り、プレイヤーには
本物の「わかりません」と区別がつきません。この 4 つ目が選ばれたら、ただの空振りとして扱います。

`はい` か `いいえ` の確率が `Answer`（既定 0.50）に届かなければ「わかりません」に倒します。
**当てずっぽうの「はい」は、このゲームで最悪の出力です。** 考えた末の「はい」と見分けがつかず、
事件がそれ一つで転びます。

### 1 ターン 1 リクエストのまま

判定を三つに分けても往復は増えません。その場にいる「訊ける人物」全員分の質問も含めて、
ルーティングと**同じリクエスト**に入れています。読むのはプレイヤーが話しかけた一人分だけで、
残りは数百トークン分の無駄になりますが、**高いのは質問の数ではなくリクエストの数**なので、
往復を増やすより安く済みます。

筋書きを state に入れるのは、訊ける人物がその場にいるターンだけです。書斎に遺体しかない
ターンに筋書きは要りません。

## フレーバー

行動と空振りのあいだが薄すぎました。まともな文章を打って「何も起こらない。」しか返って
こないと、プレイヤーは何も学ばないまま、それを何度も読むことになります。

そこで**結果を持たない文章**を置けるようにしました。雨の音、壁の古い写真、机の空のグラス。
読めますが、何も起きません。

```json
"flavours": [{
  "id": "photographs",
  "scenes": ["hall"],
  "match": { "what": "...", "not_for": "...", "examples": ["..."] },
  "did": "壁の古い写真を眺めた。",
  "text": ["..."]
}]
```

**行動として書かないのが要点です。** 効果のない行動として書くと、それはルーティングの
`choice` に並び、部屋にフレーバーを二十個置いた時点で確率が割れて、本当に必要な行動が
しきい値を越えられなくなります。フレーバーは**別の `choice` で、行動が全部外れたあとにだけ**
聞きます。だから何個書いても、行動は一つも遠くなりません。

`scenes` と `requires` は行動と同じように効くので、「そこまで知ってから見ると意味が変わる
もの」も置けます。

## 部屋に入ったら、部屋を描く

移動しても「廊下を戻ると、雨音がまた大きくなった。」の一行しか出ず、そこに何があって誰が
いるかは横のパネルを見に行くしかありませんでした。いまは、移動したターンのログに部屋の
描写が入ります。

- 場所の `description`（作者が書いたもの）
- そのあとに「望月 節子（家政婦）と久瀬 瑠依（主人の顧問弁護士）が、ここにいる。」の一行

この一行だけはエンジンが組み立てます。誰がどこにいるかは事件が進むと変わるので、ファイルに
書いておけないからです。**だから `description` には人を書かないでください**（engine が
重ねて言ってしまいます）。代わりに、調べられる物を書いてください。

開始時の部屋も同じように描かれます（`POST /api/new` の `arrival`）。

## 選択肢は見せない

これはゲームの根幹です。プレイヤーが読むのは、起きたことと、いまいる場所と、手の中の
ものだけ。**何を打てたのかは決してレスポンスに乗りません。**

- シナリオはサーバ側にしかない（バイナリに `go:embed` で埋め込み）
- 返るのは、当たった行動の結果の文章と `did`（「机を調べた。」）だけ
- 唯一の無料のヒントは「いま誰がここにいるか」「いまいる部屋に何があるか」と
  「そろそろ話がつながりそうだ」

### 辿り着かなかった真相は、最後まで言わない

エンディングの採点表は `finale.points` のラベルを ○×で並べていました。これが、**不完全な
回答をしたプレイヤーに、辿り着けなかった部分をそのまま教えてしまいます。** 「一匹分の足跡 ×」
は、その一行が真相の要約です。

いまはフロントが**当てた要素だけを名前で出し、残りは数だけ**出します（「辿り着かなかった
ことが、あと 2 つ」）。API は変わらずラベルを返します。境界を画面のところに引いてあるので、
調整用のクライアントや CLI は今までどおり全部読めます。

これは**型で縛ってあります**。ネタバレを含むテキスト（真相、`match` の説明文、採点用の
質問文）は `scenario.Hidden` 型で、`MarshalJSON` が必ずエラーを返します。レスポンスは
`encoding/json` で組み立てるので、**将来どんなハンドラを書いても、これらを含む型は
エンコードに失敗します**（漏れる代わりに 500 になる）。

モデルに渡すときだけ `scenario.Plain` で明示的に外します。型を外す場所がコード上に
一箇所だけ現れる、というのがこの仕組みの狙いです。

## 構成

```
ブラウザ ──POST /api/act──> Cloud Run ──> api.typesafe.ai
  （物語と、いる場所と、       （全事件と        （入力を分類する）
    手の中のものだけ）          API キーを持つ）
```

| エンドポイント | 役割 |
| --- | --- |
| `GET /api/cases` | 遊べる事件の一覧（ID・題・添え書きだけ） |
| `POST /api/new` | `{"case": "yakata"}` で開始。状態トークンを返す |
| `POST /api/act` | `{"state", "input"}` で 1 ターン |
| `POST /api/accuse` | `{"state", "answer"}` で推理を採点し、エンディングを返す |
| `GET /portraits/...` | 事件が持っている肖像（バイナリに埋め込み） |

**どの事件かは状態トークンの中にあります。** リクエストで指定するのは開始のときだけで、
途中のターンは自称しません。話の途中で別の事件にすり替えることはできません。

| パッケージ | 役割 |
| --- | --- |
| `internal/scenario` | 事件の中身（文章・人・場所・行動・真相）と、その検証 |
| `internal/game` | 何ができるか、何が起きるか、入力をどう行動に落とすか |
| `internal/session` | プレイ状況を署名付きトークンにしてブラウザに預ける |
| `internal/server` | HTTP。ここが「見せてよいもの」の境界 |
| `internal/jev` | System One API のクライアント（`jev-nostr` と同じもの） |
| `web` | フロントエンド（[kanabun](https://github.com/ocknamo/kanabun)）。ビルド結果は `docs/mystery/` |

`internal/jev` は jev-nostr からのコピーです。このリポジトリはサービスごとに別モジュールで、
Go は他モジュールの `internal` を import させないため、共有ではなく複製しています。

### 状態はサーバに持たない

Cloud Run はゼロまで縮み、複数インスタンスで動きます。ゲームをメモリに持つと、途中で
消えます。そこで**状態はブラウザに預け、毎ターン往復させます**。中身は秘密ではありません
（どこにいて何を見つけたか＝プレイヤーが読んだこと）が、次に何ができるかを決めてしまうので、
HMAC-SHA256 で署名しています。書き換えたトークンは 400 で弾かれます。

### しきい値は Go 側

Jev には「入力は何か」だけを聞き、「それを採用するか」は Go で決めます
（`game.Policy`）。判定はこうです。

1. 選ばれたのが `none` ではない
2. その確率が `none` の確率より大きい
3. かつ `Match`（既定 0.40）以上で、`confidence` が `Confidence`（既定 0.35）以上

`none` を選択肢として**必ず混ぜる**のが要点です。`choice` の確率は合計 1 なので、受け皿が
ないと無関係な入力が「いちばん似ていない度合いの低い行動」に流れ込みます。

同じ判定を、誰に向けた質問かにもフレーバーにも使っています。それぞれ別の `choice` なので、
**行動が増えてもクローズ質問が届きにくくなることはありません**。

既定値は測定値ではなく出発点です。`MATCH_THRESHOLD` などの環境変数と CLI のフラグで
動かせます。

## 動かす

```sh
export TYPESAFE_API_KEY=...
go run ./cmd/server           # http://localhost:8080
```

ページは `docs/mystery/`（GitHub Pages）です。ローカルのサーバに向けるには
`?api=http://localhost:8080` を付けます。

| 環境変数 | 既定値 | 内容 |
| --- | --- | --- |
| `TYPESAFE_API_KEY` | （必須） | 無いと起動しない |
| `GAME_SECRET` | （毎回ランダム） | 状態トークンの署名鍵。本番では必ず設定する |
| `JEV_MODEL` | `jev-latest` | モデル識別子 |
| `MATCH_THRESHOLD` / `CONFIDENCE_THRESHOLD` / `POINT_THRESHOLD` | 0.40 / 0.35 / 0.50 | しきい値 |
| `CLOSED_THRESHOLD` | 0.50 | 入力を「はいかいいえで答えられる質問」と見なす noul |
| `ANSWER_THRESHOLD` | 0.50 | クローズ質問で「はい／いいえ」に踏み切る確率 |
| `GAME_DEBUG` | | `1` でモデルの生の数字をレスポンスに含める（調整用） |
| `TYPESAFE_ENDPOINT` | | 接続先の差し替え（スタブ用） |

### フロントエンド

[kanabun](https://github.com/ocknamo/kanabun)（`@kanabun/core` + `@kanabun/router`）で
書いてあります。ソースは `web/`、ビルド結果は `docs/mystery/` です。

```sh
cd web
bun install
bun run dev      # 開発サーバ
bun run build    # docs/mystery/ を作り直す
```

**ビルド結果をコミットしています。** GitHub Pages は `docs/` をブランチからそのまま配信する
ので、出力がリポジトリに無いとページが出ません。CI が `bun run build` を実行して
`docs/mystery/` に差分が出ないことを確認します（差分が出たら、ソースだけ変えてビルドし忘れた、
ということです）。

**Bun のバージョンは `.bun-version` で固定しています。** Bun の出力はバージョンで変わり、
チャンクのファイル名に入るコンテンツハッシュまで変わります（1.3.11 と 1.4.2 で実際に違いました）。
固定して初めて、CI の再ビルドが「比較」になります。ビルドするときは `.bun-version` の版を
使ってください。

`--no-sourcemap` を付けても `.map` が出るため、ビルドスクリプトの最後で消しています。

#### `#name` のハッシュルーティング

事件ごとに URL があります。いまは `#yakata` の一本で、`#` だけなら事件簿の一覧です。

- ハッシュはサーバに送られないので、GitHub Pages に rewrite の設定が要りません。
  リロードしてもディープリンクが生きます（`createHashSource`）。
- 一覧のリンクは `<Link>` ではなく素の `<a href="#yakata">` です。ルータの `navigate` は
  パスを絶対化するので `#/yakata` になってしまい、`#name` になりません。ハッシュソースは
  `hashchange` を購読しているので、素のアンカーでもルータはついてきます。

#### ルート直下はフラグメントにしない

kanabun にコンパイラは無く、**関数が遅延のしるし**です。コンポーネントがフラグメントを返すと、
`<Routes>` は `<Show>` などのサンクが入った配列を受け取り、それを自分のエフェクトの中で読みます。
するとサンクが触ったシグナルがルート自体の依存になり、状態が変わるたびにルートが再生成されます。
`resource` を持つコンポーネントなら、そのまま fetch の無限ループです（実際に踏みました）。

コンポーネントのルートは要素ひとつにしてください。そうすれば各サンクが自分のエフェクトを持ちます。
同じ理由で、`<Router>` の children も関数です（`<Router>{() => <Shell />}</Router>`）。

### CLI で測る

このゲームの成否は、ほぼ一点にかかっています。**プレイヤーが実際に打つ日本語が、
狙った行動に当たるか。** これは議論ではなく計測の対象なので、計測できるようにしてあります。

```sh
go run ./cmd/cli -script testdata/walkthrough.txt -accuse testdata/solution.txt
```

`walkthrough.txt` は `入力<TAB>当たるべき行動 ID` です（`none` は「何にも当たらないのが
正解」、`closed:kurata` はクローズ質問、`flavour:rain` はフレーバー）。実行の最後に何件中
何件が狙いどおりだったかが出ます。スクリプトを省くと標準入力を読むので、ターミナルで
そのまま遊べます。

**入力は `match.examples` から取らないでください。** モデルに見せている文をそのまま打ち込む
walkthrough は、何も測っていません。

`-v` を付けると、そのターンに何が選択肢として出ていたかも表示されます。

## 事件を書く

`internal/scenario/data/*.json` に置くと、**ファイル名がそのまま事件の ID とページのハッシュ**
になります（`yakata.json` → `#yakata`）。起動時に全部読み込んで検証するので、参照の
壊れたシナリオはサービスが起動しません。

```json
{
  "id": "...", "title": "...",
  "opening": ["..."], "incident": ["..."],
  "start_scene": "hall",
  "scenes":     [{ "id": "hall", "name": "...", "description": ["..."], "characters": ["..."] }],
  "characters": [{
    "id": "...", "name": "...", "role": "...", "avatar": "👩‍💼",
    "image": "portraits/yakata/mochizuki.png",
    "closed": {
      "knows": ["この人物が見たこと・したこと・聞かされたこと"],
      "hides": ["知っているが認めないこと（犯人なら自分の犯行）"],
      "answers": { "yes": "「はい」", "no": "「いいえ」", "unknown": "「存じません」" }
    }
  }],
  "evidence":   [{ "id": "...", "name": "...", "description": "..." }],
  "actions": [{
    "id": "examine_ledger",
    "scenes": ["hall"],
    "requires": { "evidence": ["..."], "flags": ["..."], "not_flags": ["..."] },
    "match": { "what": "...", "not_for": "...", "examples": ["...", "..."] },
    "speaker": "mochizuki",
    "did": "献立帳を調べた。",
    "result": ["..."], "repeat": ["..."],
    "gives_evidence": ["meals"], "sets_flags": ["..."], "moves_to": "chamber"
  }],
  "flavours": [{
    "id": "photographs",
    "scenes": ["hall"], "requires": { "...": "..." },
    "match": { "what": "...", "not_for": "...", "examples": ["..."] },
    "did": "壁の写真を眺めた。",
    "text": ["..."]
  }],
  "misses": { "default": ["..."], "move": ["..."], "ask": ["..."], "declare": ["..."] },
  "finale": { "...": "..." }
}
```

`avatar` は必須の一文字で、`image` は任意です。`image` を書くとその絵が肖像になり、
書かなければ `avatar` がそのまま肖像になります。**絵が読み込めなかったときも `avatar` に
戻る**ので、絵を付けた人物にも `avatar` は要ります（無いとシナリオが読み込めません）。
`image` に書けるのは `http` / `https` の URL か、**サービスから見た相対パス**だけです。
`data:` や `javascript:` は絵ではないので弾きます。

**肖像は `internal/scenario/data/portraits/<事件 ID>/` に置きます。** 事件の JSON と同じく
バイナリに埋め込まれ、`GET /portraits/...` で配られます。`image` に
`portraits/yakata/ruise.png` と書けば、ページは**いま話している相手のサービス**に対して
それを解決します（`?api=` でローカルに向ければ、絵もそちらから来ます）。肖像は事件の一部で、
事件はこちら側にあるので、絵だけページの隣に置く理由がありません。

**`avatar` には人物の絵文字を使ってください。** 肖像は顔の並ぶ欄に出るので、道具の絵文字を
混ぜると「持ち物」ではなく「顔が抜けている人」に見えます。役柄は隣に文字で出ているので、
`avatar` が仕事道具を表す必要はありません。

書くときのコツは七つです。

1. **`match` は排他的に書く。** `choice` の確率は合計 1 なので、「書斎を調べる」と
   「書斎の机を調べる」が並ぶと票が割れて共倒れします。紛らわしい組には `not_for` を
   必ず入れてください。`what` だけをいくら足しても分かれません。
2. **難易度は `requires` で作る。** 条件を満たさない行動はそもそも Jev に見せないので、
   「まだできない」は自動的に「何も起こらない」になります。
3. **空振りの文章を手を抜かずに書く。** 序盤にプレイヤーがいちばん多く読むのは空振りです。
   だから `misses` は intent ごとに分かれています。
4. **`closed.knows` はその人物の視界に限る。** 筋書き全体は state から見えるので、`knows` は
   「この人物がどこまで見たか」を絞る役です。書きすぎると全員が真相を知っていることになります。
5. **`closed.hides` には犯行だけでなく「ついた嘘」も書く。** 実測で見つけました。犯人の
   `hides` に犯行しか書いていないと、アリバイの嘘を突かれたときに否定ではなく「わかりません」で
   逃げます。一時間前に茶を運んだかどうかを覚えていない秘書は、隠しているのではなく壊れています。
   嘘そのものを `hides` に挙げると、嘘を貫くほうを選びます。
6. **`scenes[].description` に人を書かない。** 誰がいるかはエンジンが一行足します。書くのは、
   調べられる物と、部屋の様子です。
7. **フレーバーは惜しまず書く。** 行動が全部外れたあとにしか聞かれないので、いくつ書いても
   行動は遠くなりません。序盤に読まれる分量がいちばん多いのはここです。

`finale.points` は真相の要素ひとつにつき `noul` ひとつ。まとめて「合っているか」を聞かない
のは、**犯人を当てた人とトリックまで見抜いた人の差がエンディングを決める**からで、単一の
判定にはその差が乗りません。8 問聞いても並列に評価されるのでコストはほとんど変わりません。

`label` は**当てた人にだけ見える名前**です。当てられなかったぶんは数だけ出るので、
「一匹分の足跡」のように、一行でその要素を言い切る名前をつけて構いません。

`endings` は上から順に判定し、最初に条件を満たしたものが採用されます。最後の一つは無条件で
なければならず、そうでなければ読み込み時に落ちます。

`finale.culprit` は一人ですが、**答えが一人でない事件**もあります（二人がかりの犯行、あるいは
三人が実は一人だった、など）。採点の `choice` は選択肢をひとつ返すので、その場合は
`finale.also_culprit` に残りを並べてください。そのうちの誰を名指ししても「犯人を当てた」に
なります。それ以外は何も変わりません（容疑者の並びも、真相の採点も、`points` のままです）。

## まだ無いもの

- **レート制限がありません。** 1 ターン = 有料 API 1 リクエストです。公開して遊ばせるなら
  Cloud Run の同時実行数だけでは足りません。
- **事件が一本しかありません。** 動作確認用に書いた 2 本（`clockwork` と `curtain`）は
  この事件に置き換えました。エンジンは事件をいくつでも持てるので、増やすぶんには
  `internal/scenario/data/` に JSON を置くだけです。
- **日本語での当たり方が未測定です。** 質問文は英語、選択肢の説明とプレイヤーの入力は
  日本語という組み合わせで書いてあります。上の CLI を CI から回すのが、それを測る唯一の手です。
